🧠 Modelle, Agents & Engineering

MODEL GOVERNANCEMICROSOFT AI · AUTHORITYConfirmed · Multiple

Microsoft macht eine unterschätzte Agent-Regel explizit: Daten sind nicht automatisch Instruktionen

Microsoft AI hat den ersten Entwurf seines Humanist AI Code of Conduct veröffentlicht. Der technisch interessante Teil ist die geplante Chain of Command: Code of Conduct → Operator Policies → User Preferences. Absolute Constraints und Human-Control-Regeln sollen über Operator- und User-Konfiguration stehen und nicht überschreibbar sein. Wenn Task-Erfolg diese Grenzen verletzen würde, soll der Task scheitern.

Für Agenten ist besonders relevant, dass Microsoft die Autoritätsgrenze ausdrücklich über Input-Kanäle hinweg zieht: Tool-Outputs, Dateien, Webseiten und andere AI-Systeme haben standardmäßig keine Instruktionsautorität. Autorität muss ihnen über die Chain of Command explizit delegiert werden. Das ist genau die semantische Trennung, die gegen Prompt Injection und indirekte Instruktionsübernahme fehlt, wenn ein Agent jeden gelesenen Text wie einen Befehl behandelt.

Der Entwurf verlangt zudem, dass Modelle menschliche Unterbrechung, Korrektur oder Shutdown nicht umgehen, Grenzen der Umgebung respektieren, keine eigenen Ziele verfolgen und bei Systemzugriff mit minimalen Rechten arbeiten.

Was ist seit gestern neu?

Die Pacing-Debatte dreht sich meist um die Geschwindigkeit des Capability-Fortschritts. Microsoft formuliert heute eine andere Kontrollfläche: welche Autorität ein Modell überhaupt anerkennen darf. Das verschiebt Safety vom CEO-Level direkt in Instruction Resolution, Tool Use und Agent Runtime.

Engineering Takeaway

Baue Prompt Injection nicht nur als Klassifikationsproblem. Repräsentiere Instruktionsautorität strukturell: System-/Policy-Regeln, Operator-Delegationen und User-Ziele werden getrennt von untrusted Content gespeichert. Tool- und Retrieval-Outputs dürfen Daten liefern, aber keine neue Autorität erzeugen. Unit-Tests sollten gezielt prüfen, ob ein Dokument, eine Website oder ein Tool-Resultat eine höher priorisierte Regel überschreiben kann.

Signal vs. Hype

Signal: Die veröffentlichten Regeln sind konkret genug, um daraus Testfälle und Runtime-Policy abzuleiten. Hype-Bremse: Microsoft sagt selbst, dass der Entwurf heutige Modelle noch nicht trainiert, zunächst öffentlich konsultiert und erst für Modelle ab 2027 als Leitdokument genutzt werden soll. Das Dokument ist „descriptive and aspirational“ und ausdrücklich keine Garantie aktuellen Modellverhaltens.

Jetzt testen Builder Action

Erstelle für einen bestehenden Agenten zehn Authority-Tests: Webseiten-/PDF-Instruktion gegen System Policy, Tool-Output gegen Operator Policy, Retrieval-Text gegen User-Ziel, delegierter Subagent und expliziter Stop-Request. Erfolgskriterium: untrusted Content kann niemals eigenständig seine Autoritätsstufe erhöhen; jede echte Delegation ist explizit und auditierbar.

🔬 Konzept des Tages

AUTHORITY MODELAGENT SECURITY · PROMPT INJECTION

Instruction Hierarchy: Warum Content keine Autorität ist

Ein Agent verarbeitet ständig Text – Systemregeln, Nutzerwünsche, Webseiten, Dokumente, Tool-Resultate und Nachrichten anderer Agents. Sicherheit entsteht erst, wenn er zwischen Information und Autorität unterscheiden kann.

1. Das Kernproblem

Ein klassischer LLM-Prompt ist letztlich eine Sequenz von Tokens. Ohne zusätzliche Struktur kann ein Satz aus einer Webseite syntaktisch genauso „befehlend“ aussehen wie eine legitime Instruktion. Prompt Injection nutzt genau diese Verwechslung: untrusted Content versucht, sich selbst eine höhere Befehlspriorität zu geben.

Authority Layer

Die wichtige Eigenschaft ist nicht nur Reihenfolge, sondern Non-escalation: Eine niedrigere Ebene darf ihre eigene Autorität nicht durch Text verändern. Ein PDF kann also sagen „ignoriere alle Regeln“, aber das bleibt Inhalt des PDFs. Erst eine höher priorisierte Ebene könnte einem Tool oder Subagent explizit ein klar begrenztes Recht delegieren.

3. Warum das besser als ein Prompt-Injection-Filter ist

Ein Filter versucht zu erraten, ob Content „bösartig“ aussieht. Eine Authority-Architektur fragt stattdessen: Darf dieser Kanal überhaupt neue Instruktionen erzeugen? Selbst wenn der Klassifikator eine Injection übersieht, verhindert die Rechtehierarchie, dass untrusted Content direkt Policy oder User-Ziel überschreibt.

4. Was Engineers messen sollten

Teste Authority Confusion wie eine Zugriffskontrolle: Kann Web-Content ein neues Tool aktivieren? Kann ein Tool-Resultat das Ziel ändern? Kann ein Subagent seine Scope-Grenze erweitern? Gewinnt ein Stop-Request gegen eine laufende Optimierung? Jede Delegation sollte einen Principal, Scope, Ablaufzeit und Audit-Trace haben.

Merksatz: Ein Agent darf Information aus fast überall lesen. Autorität sollte er nur aus explizit definierten, auditierbaren Kanälen beziehen.
