Warum relevant?

Ein stabiler API-String ist kein stabiler Modellvertrag. Für reproduzierbare Evals, Audit-Trails, regulierte Workflows und Regression Detection reicht es nicht, nur model=deepseek-v4-pro zu speichern. Entscheidend ist, welcher immutable Model-Build tatsächlich geantwortet hat – und ob Provider diesen resolved state überhaupt sichtbar machen.

Engineering Takeaway

Behandle Provider-Aliase wie latest-Tags in Container-Registries: bequem für Default-Nutzung, aber ungeeignet als alleinige Reproduzierbarkeits-ID. Logge mindestens Requested Model, Provider, Zeit, Parameter, Preisregime und – falls vorhanden – Resolved Model/Version. Definiere Provider-Migrationen als Canary-/Regression-Gate: dieselben repräsentativen Tasks vor und nach dem Cutover, Task Success statt nur HTTP 200 messen.

🔬 Konzept des Tages

AI ENGINEERING CONCEPTMODEL ALIAS DRIFT

Model Alias Drift: Warum ein stabiler API-Name kein stabiles Modell ist

AI-APIs sehen oft aus wie klassische versionierte Services: Man sendet einen Model-Namen und erwartet reproduzierbares Verhalten. In Wirklichkeit kann der Name nur ein Alias auf eine veränderliche Serving-Konfiguration sein. Wenn der Provider das Backend austauscht, bleibt dein Request syntaktisch identisch – aber dein System hat faktisch eine neue Dependency bekommen.

Die Intuition

Denke an Container-Tags: my-service:latest ist bequem, aber kein unveränderlicher Build. Ein Digest wie sha256:... ist reproduzierbar. Bei Model-APIs ist deepseek-v4-pro, latest oder ein familienweiter Name häufig näher am Tag als am Digest. Der Provider kann Routing, Quantisierung, System-Prompt, Safety Layer, Reasoning Defaults oder das Modell selbst ändern.

requested_model
deepseek-v4-pro

Warum das für Evals gefährlich ist

Wenn du Montag und Freitag denselben Eval gegen denselben Model-Namen laufen lässt, kann ein Score-Unterschied drei Ursachen haben: dein Code, dein Testset – oder ein unsichtbarer Provider-Cutover. Ohne aufgelöste Modellversion fehlt dir die Provenance. Das ist besonders problematisch bei Regression Gates, regulierten Entscheidungen und Langzeit-Benchmarks.

Der robuste Vertrag

Ein guter AI-API-Vertrag hat zwei Ebenen: Convenience Alias für normale Produktnutzung und immutable Version Identity für Reproduzierbarkeit. Wenn der Provider keine immutable ID anbietet, muss dein eigenes Audit mindestens Provider, Requested Model, Timestamp, Parameter, Response-Metadaten, Preisregime und relevante Output-Fingerprints speichern. Große Provider-Migrationen werden wie Dependency-Upgrades behandelt: Canary, A/B oder Replay-Eval vor breitem Rollout.

request provenance = {
  provider,
  requested_model,
  resolved_model_or_version,
  timestamp,
  parameters,
  pricing_tier,
  eval_fixture_version
}

if resolved_model changed:
    run_regression_gate()

Wann Open Weights helfen

Ein gepinnter Checkpoint auf Hugging Face oder im eigenen Artifact Store ist viel näher an einem immutable Digest: Gewichte, Commit/Revision, Runtime und Quantisierung können festgeschrieben werden. Dafür übernimmst du Serving- und Infrastrukturverantwortung. Die Wahl lautet deshalb nicht „API schlecht, self-hosting gut“, sondern: Welche Reproduzierbarkeitsgarantie brauchst du für diesen Workload?

Merksatz

Ein Model-Name ist nur dann eine Version, wenn der Anbieter garantiert, dass er auf denselben unveränderlichen Build zeigt. Sonst ist er ein Alias – und Aliase gehören in deine Change-Management- und Eval-Pipeline.
