Why it matters

Engineering Takeaway

Treat provider aliases like latest tags in container registries: convenient for default use, but unsuitable as the only reproducibility identifier. At minimum log Requested Model, provider, timestamp, parameters, pricing regime and — if available — Resolved Model/Version. Treat provider migrations as a canary/regression gate: replay the same representative tasks before and after cutover and measure task success, not merely HTTP 200s.

🔬 Concept of the Day

AI ENGINEERING CONCEPTMODEL ALIAS DRIFT

Model Alias Drift: Why a Stable API Name Is Not a Stable Model

AI APIs often look like conventionally versioned services: you send a model name and expect reproducible behavior. In reality, the name may only be an alias to a mutable serving configuration. If the provider swaps the backend, your request remains syntactically identical — while your system has effectively acquired a new dependency.

The intuition

Think about container tags: my-service:latest is convenient, but it is not an immutable build. A digest such as sha256:... is reproducible. In model APIs, deepseek-v4-pro, latest or a family-wide name may be closer to a tag than a digest. The provider can change routing, quantization, system prompts, safety layers, reasoning defaults or the model itself.

Why this is dangerous for evals

If you run the same eval on Monday and Friday against the same model name, a score change can have three causes: your code, your fixture — or an invisible provider cutover. Without a resolved model version, provenance is incomplete. This becomes especially problematic for regression gates, regulated decisions and longitudinal benchmarks.

The robust contract

A strong AI-API contract has two levels: a convenience alias for normal product use and an immutable version identity for reproducibility. If the provider offers no immutable ID, your own audit trail should at least record provider, Requested Model, timestamp, parameters, response metadata, pricing regime and relevant output fingerprints. Large provider migrations should be handled like dependency upgrades: canary, A/B or replay eval before broad rollout.

request provenance = {
  provider,
  requested_model,
  resolved_model_or_version,
  timestamp,
  parameters,
  pricing_tier,
  eval_fixture_version
}

if resolved_model changed:
    run_regression_gate()

When open weights help

A pinned checkpoint on Hugging Face or in your own artifact store is much closer to an immutable digest: weights, commit/revision, runtime and quantization can be fixed. In exchange, you take on serving and infrastructure responsibility. The choice is therefore not “API bad, self-hosting good,” but: what reproducibility guarantee does this workload require?

Rule of thumb

A model name is only a version if the provider guarantees that it points to the same immutable build. Otherwise it is an alias — and aliases belong in your change-management and eval pipeline.
